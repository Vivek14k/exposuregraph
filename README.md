# ExposureGraph

ExposureGraph is a cybersecurity SaaS MVP designed for individual developers and small startups to discover, map, and evaluate their external attack surfaces and security exposure.

---

## 🎯 Overview

Modern cloud-native developers and startups often struggle with visibility across fragmented external digital assets (domains, subdomains, cloud resources, open ports, exposed services). ExposureGraph provides a clear, graph-driven approach to:
- **Discover Attack Surfaces**: Enumerate domain/subdomain hierarchies, DNS records, and exposed network endpoints.
- **Model Relationships (Graph)**: Map interconnected assets and exposures to pinpoint vulnerabilities and blast radiuses.
- **Prioritize Risk**: Evaluate exposure severity through an actionable risk engine tailored for lean teams.

## 🚀 Getting Started

### Prerequisites

- Python compatible with the packages in `backend/requirements.txt`
- Node.js and npm

### Setup

Create and activate a virtual environment, then install dependencies and create a private local environment file:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend/requirements.txt
Copy-Item .env.example .env
cd frontend
npm ci
```

Edit `.env` with local settings and provider credentials as needed. Never commit `.env`.

## 🔒 Security & Best Practices

- Never commit secrets, credentials, or `.env` files to source control.
- Provider keys were previously present in the shareable environment example. Revoke and replace the Gemini and Gnani keys before publishing, even though the example now contains blank values. If either key was ever committed or shared, removing it from the latest files does not remove it from history.
- Keep local scan data such as `exposuregraph.db` private; it is excluded by `.gitignore`.
- Scans and discovery operations must strictly target domains and assets owned by or authorized for assessment.
- Authentication uses database-backed sessions, per-user scan ownership, CSRF tokens, and password hashing. Public account registration is disabled; create accounts through the administrator CLI.
- Production configuration requires DNS TXT domain verification. The local demo mode is only a user attestation and does not prove domain ownership.
- Scanner probes are limited to ports 80, 443, 8080, and 8443, do not follow redirects, reject non-public addresses, pin HTTP connections to validated IPs, verify TLS certificates, and cap response bodies and scan time.

## Runtime modes and limits

Assistant answers are generated by **Gemini 2.5-Flash** (via `google-genai`) and grounded in scan evidence through function-calling tools. The assistant retains a bounded recent conversation history for follow-up context and mirrors detected speech language without carrying a prior voice locale into typed messages. Risk scores remain deterministic. The LLM brain never issues authorization tokens and falls back to evidence-based deterministic replies if Gemini is unavailable. **Gemini and Gnani keys serve different roles:** `GEMINI_API_KEY` enables natural-language reasoning; `GNANI_API_KEY` enables Prisma speech recognition and Timbre speech output. Both are used in voice conversations when configured; Gnani is not an alternate text-generation provider. Without the Gemini key, text replies use the deterministic fallback.

SQLite is intended for local development. A production deployment recipe is not included in this repository. Production deployments should use PostgreSQL and a single database-locked scan worker; keep the database and API off public ports and place the frontend behind a TLS-terminating ingress. Do not scale the worker beyond one instance; scan execution and interruption recovery are designed for a single active worker.

The scanner performs best-effort DNS discovery for a bounded list of common hostnames and checks HTTP/TLS behavior. Its coverage is not a penetration test and a timeout or unavailable host does not establish that a vulnerability exists. Reports contain only saved scan data.

## Run locally

Install backend dependencies and create an administrator account using the database configured for your local environment. The app does not auto-create tables; run the migration first. Existing SQLite data is preserved and legacy scans remain unowned until explicitly claimed.

**Backend**

```powershell
.\.venv\Scripts\Activate.ps1
python -m alembic upgrade head
python -m backend.cli create-user analyst@example.com
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --reload
```

The health check is at `http://127.0.0.1:8000/health`. API docs are enabled only when `DEBUG=true`.

**Frontend**

```powershell
cd frontend
npm run dev -- --host 127.0.0.1
```

Open `http://127.0.0.1:5173`, sign in with the account created above, and select Text mode if microphone permission or browser audio support is unavailable. Set `DOMAIN_AUTH_MODE=demo_attestation` for a local demo or `dns_txt` to require a DNS proof.

The local Vite server proxies `/api` to `http://127.0.0.1:8000`. Configure `GEMINI_API_KEY` for generated assistant replies and `GNANI_API_KEY` for voice transcription and speech output; the assistant footer shows the active reply and speech providers.

## Production deployment

Deployment manifests and a production Compose file are not included. Before deploying, configure a stable random `SESSION_SECRET` (at least 32 characters), HTTPS with `COOKIE_SECURE=true`, `DOMAIN_AUTH_MODE=dns_txt`, a production database, and narrowly scoped CORS origins. Keep database and API ports private, use a TLS-terminating reverse proxy, and run only one scan worker. Back up the database and review migrations before applying them. The initial migration preserves legacy scans as unowned; use `--claim-legacy-scans` only when assigning every legacy scan to one account is intentional.
